# What an idle TCP connection holds

Issue #613: the "per idle TCP" cell of the second competition round
(`2026-11-05-competition.md`), 8.7 KB, split by where the memory is.

4-core arm64 VM (7.7 GiB, Linux 7.0.0-38-generic), glibc's malloc. elodin
release builds of `e5f802f` (main) and of the #613 head. The shape is the
harness's: 1,000 clients each ask one cached name over TCP and hold the
connection; per connection is (RSS held − RSS before) ÷ 1,000, read 1.5 s after
the last answer, so every connection has idled past `loop.IDLE_TRIM_AFTER`
(250 ms). Where the memory sits comes from `/proc/<pid>/smaps` diffed by mapping
before and while held, and the fiber stacks' resident pages from
`/proc/<pid>/mem`.

## Main: 8.7 KB

Two runs each, back to back: 8.68 / 8.68 KB.

| where | per connection |
|---|---|
| fiber stack: the page the parked stack pointer is in | 4.0 KB |
| the fiber's scratch: the first 16 KiB block `arena_free_all` keeps mapped, of which the query touched the page its header is in | 4.0 KB |
| malloc: the `Fiber` (256 B), its fd watch and two waiter slots, the `Conn_Entry` and `Stream_Job`, the loop's map slot, glibc's headers and arena slack | ~0.7 KB |

The scratch is empty during the idle wait: `serve_dns_stream` frees it after
every answer. Its block was kept only so the next query on the connection need
not map one.

## #613: 4.7 KB

The idle trim that hands back the stack (#596) now unmaps the scratch too when
nothing in it is live (`loop.scratch_release`). Two runs: 4.68 / 4.68 KB.

The issue's harness (`go run ./cmd/bench -only compare -servers elodin
-mock-cpus 2-3 -binary …`) on the #613 release binary:

| build | per idle TCP | per idle DoT | per idle DoH/2 | per query in flight |
|---|---|---|---|---|
| main (`2026-11-05-competition.md`, #614) | 8.7 KB | 43 KB | 43 KB | 17 KB |
| #613 | **4.7 KB** | **39 KB** | **39 KB** | 17 KB |

DoT and DoH/2 give back the same scratch page; a query in flight is not idle and
keeps its scratch.

## What is left, and why

- **The stack page, 4 KB.** 999 of the 1,000 connection fibers have exactly one
  page resident: the stack pointer is in the top page, so nothing under it is
  left to trim. A page is the least the kernel backs, and a parked fiber's frames
  have to be somewhere. The servers at 0.1-0.2 KB (PowerDNS Recursor, dnsdist,
  Unbound) keep an idle connection as a state machine with no stack. Rewriting
  the connection path that way is the same trade #614 declined for a query in
  flight. Copying the parked frames to the heap and back on wake would make
  every pointer into a parked stack a use-after-free risk, to save part of a page.
- **The malloc, ~0.7 KB.** Each item is live for the connection's life: the
  fiber, the epoll watch that wakes it, the connection table's entry.
